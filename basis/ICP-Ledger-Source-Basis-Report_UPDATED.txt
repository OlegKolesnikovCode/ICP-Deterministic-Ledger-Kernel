4. Project Identity

ICP Deterministic Ledger Kernel

4.2 One-Sentence Description

A transfer-only, multi-canister correctness kernel on ICP that proves idempotent, append-only, upgrade-safe balance mutation through explicit authority boundaries and a single local Ledger Core commit path.

4.3 Core Thesis

The project is not primarily a finance app.

The project is a correctness-preserving execution architecture.

It proves that balance-affecting operations on ICP can be constrained through:

isolated canister authority
deterministic state transitions
single authoritative mutation path
idempotent request handling

append-only journal proof

upgrade-safe stable state

6. Primary Architectural Decision
ADR-001 — Ledger Core Owns Journal and Balance Mutation
Decision

The MVP MUST use this model:

Ledger Core Canister owns:
  - accounts
  - assets
  - balances
  - operation records
  - idempotency records
  - append-only journal entries
  - authoritative commit logic
Rejected Model

The MVP MUST NOT use this design:

Ledger Core Canister mutates balances.
Separate Journal Canister appends ledger entries later.
Rationale

A separate Journal Canister introduces cross-canister partial-commit risk.

Bad sequence:

1. Ledger Core mutates balance.
2. Ledger Core calls Journal Canister.
3. Journal append fails.
4. Balance changed without authoritative journal proof.

This violates the core invariant:

INV-001:
Every balance change MUST have one or more authoritative LedgerEntry records.

ICP’s message execution model supports this design decision: single canister message execution is atomic and sequential, but inter-canister calls can split execution into multiple message executions. ICP’s docs also state that methods using inter-canister calls are not atomic across the full method, and failures may not roll back all prior state changes.

7.3 Authority Rules
AUTH-001:
Gateway decides whether a request is well-formed and allowed to enter the system.

AUTH-002:
Ledger Core decides whether the request is financially valid and commit-safe.

AUTH-003:
Only Ledger Core may authorize and commit balance-affecting operations.

AUTH-004:
Ledger Core MUST read immediateCallerPrincipal from ICP execution context.

AUTH-005:
Ledger Core MUST NOT accept debitAuthorityPrincipal from arbitrary user request body.

AUTH-006:
For Transfer, debitAuthorityPrincipal MUST equal sourceAccount.ownerPrincipal.

AUTH-007:
Gateway MAY authenticate caller identity, but Gateway MUST NOT be the final debit authority.

AUTH-008:
Ledger Core MUST independently verify debit authorization before commit.

AUTH-009:
Read Model MUST NOT make authorization decisions for balance-affecting operations.

AUTH-010:
Admin/bootstrap authority MUST be explicitly separated from user transfer authority.

AUTH-011:
If Gateway is in the write path, Ledger Core MUST treat immediateCallerPrincipal as the Gateway Canister principal, not as the original external user.

AUTH-012:
If Gateway is in the write path, Ledger Core MUST accept originalCallerPrincipal only through a Gateway-authenticated envelope.

AUTH-013:
Ledger Core MUST verify that immediateCallerPrincipal is an authorized Gateway Canister before using any Gateway-attested originalCallerPrincipal.

AUTH-014:
If immediateCallerPrincipal is not an authorized Gateway Canister, Ledger Core MUST reject Gateway-envelope execution.

AUTH-015:
Gateway-authenticated envelope fields MUST be constructed by Gateway from ICP execution context and normalized request data; they MUST NOT be copied from arbitrary user body fields.

AUTH-016:
Ledger Core MUST use debitAuthorityPrincipal, not Gateway immediateCallerPrincipal, when checking sourceAccount.ownerPrincipal.

AUTH-017:
Direct Ledger Core calls MAY be allowed only if SRC-01 explicitly defines direct-call authorization semantics; otherwise Gateway-envelope execution is the MVP write-path model.

7.4 Caller Identity Model

The MVP uses the following write identity model:

Frontend / User calls Gateway Canister.
Gateway reads the external caller from ICP execution context.
Gateway constructs a normalized authenticated request envelope.
Gateway calls Ledger Core.
Ledger Core sees Gateway as immediateCallerPrincipal.
Ledger Core verifies Gateway is authorized.
Ledger Core uses Gateway-attested originalCallerPrincipal as debitAuthorityPrincipal only after verifying the Gateway envelope.

AUTH-CALLER-001:
originalCallerPrincipal means the external user principal authenticated by Gateway.

AUTH-CALLER-002:
immediateCallerPrincipal means the principal returned by ICP execution context in the currently executing canister method.

AUTH-CALLER-003:
debitAuthorityPrincipal means the principal Ledger Core uses for Transfer debit authorization.

AUTH-CALLER-004:
In Gateway-mediated execution, debitAuthorityPrincipal MUST equal originalCallerPrincipal after Gateway authorization is verified.

AUTH-CALLER-005:
In Gateway-mediated execution, debitAuthorityPrincipal MUST NOT equal immediateCallerPrincipal unless the Gateway Canister itself is the source account owner.

AUTH-CALLER-006:
Any generated implementation that checks sourceAccount.ownerPrincipal against the Gateway Canister principal instead of the authenticated external user principal violates the authority model.

14. Idempotency and Replay Rules
14.1 Idempotency Key

The idempotency key MUST be:

debitAuthorityPrincipal + operationType + requestId

For Gateway-mediated execution, debitAuthorityPrincipal is the Gateway-authenticated originalCallerPrincipal verified by Ledger Core.

The idempotency key MUST NOT be only:

requestId

The idempotency key MUST NOT use immediateCallerPrincipal alone when the immediate caller is Gateway.
14.2 Idempotency Record
type IdempotencyRecord = {
  idempotencyKey: string;
  debitAuthorityPrincipal: string;
  immediateCallerPrincipal: string;
  operationType: "TRANSFER";
  requestId: string;
  status: "COMMITTED" | "REJECTED" | "IN_PROGRESS";
  operationId?: string;
  responseHash: string;
  deterministicResponse: string;
  createdAt: bigint;
  completedAt?: bigint;
  recoveryState?: "NONE" | "STALE_IN_PROGRESS" | "RECOVERY_REQUIRED";

14.3 Duplicate Behavior
Prior Result	Required Duplicate Behavior
COMMITTED	Return same committed result
REJECTED	Return same rejected result
IN_PROGRESS	Return deterministic retry-safe response
14.4 Rules
IDEMP-001:
Duplicate requests MUST NOT create duplicate balance effects.

IDEMP-002:
Duplicate requests MUST NOT create duplicate ledger entries.

IDEMP-003:
Duplicate requests MUST return the same deterministic outcome for the same idempotency key.

IDEMP-004:
Rejected requests SHOULD be stored as deterministic idempotency outcomes when rejection reason is deterministic.

IDEMP-005:
If an idempotency record is IN_PROGRESS, duplicate calls MUST return a deterministic retry-safe response.

IDEMP-006:
IN_PROGRESS records MUST NOT be treated as committed.

IDEMP-007:
IN_PROGRESS records MUST NOT create duplicate balance effects.

IDEMP-008:
If commit succeeds, idempotency status MUST become COMMITTED.

IDEMP-009:
If deterministic validation fails, idempotency status SHOULD become REJECTED.

IDEMP-010:
If non-deterministic system failure occurs before commit, the system MUST NOT expose partial committed state.

IDEMP-011:
The same requestId from two different debitAuthorityPrincipals MUST produce different idempotency keys.

IDEMP-012:
The same requestId from the same debitAuthorityPrincipal but different operationType MUST produce different idempotency keys.

IDEMP-013:
Idempotency outcomes MUST survive Ledger Core canister upgrade.

IDEMP-014:
Idempotency lookup MUST occur before any new balance mutation is attempted.

IDEMP-015:
IN_PROGRESS outcomes MUST have a deterministic recovery policy.

IDEMP-016:
If Ledger Core traps before authoritative commit, the system MUST NOT persist a COMMITTED idempotency outcome.

IDEMP-017:
A stale IN_PROGRESS record MUST resolve only through a source-defined recovery path.

IDEMP-018:
Duplicate IN_PROGRESS response body MUST be canonical and replay-stable.

IDEMP-019:
Upgrade recovery MUST preserve COMMITTED and deterministic REJECTED idempotency outcomes before attempting any IN_PROGRESS repair.

IDEMP-020:
An IN_PROGRESS record MUST NOT be converted to COMMITTED unless the corresponding authoritative Operation and required LedgerEntry records exist.

IDEMP-021:
An IN_PROGRESS record MAY be converted to deterministic REJECTED only if source-defined recovery proves no authoritative commit occurred and the rejection class is deterministic.

IDEMP-022:
An unresolved stale IN_PROGRESS record MUST put the affected idempotency key into retry-safe recovery state and MUST NOT allow duplicate balance effects.

IDEMP-023:
Idempotency keys MUST be derived from canonical normalized values, not raw request strings.

IDEMP-024:
Idempotency replay equality MUST compare canonical deterministic response serialization.

16. Atomic Commit Rules

ICP canister methods involving inter-canister calls may create multiple message execution boundaries. The ICP docs state that each message handler is atomic on its own, but traps only roll back changes in the current message handler, not earlier handlers. The docs also warn that multiple inter-canister calls are asynchronous and a later failure does not roll back prior state effects.

Therefore:

ATOMIC-001:
Ledger correctness is atomic only inside the Ledger Core Canister authoritative state transition.

ATOMIC-002:
Cross-canister calls MUST be treated as asynchronous, fallible, and non-transactional.

ATOMIC-003:
No cross-canister call may be required to complete the authoritative balance/journal commit in MVP.

ATOMIC-004:
Read Model update failure MUST NOT roll back Ledger Core commit.

ATOMIC-005:
Journal creation failure MUST invalidate balance mutation because journal is authoritative and lives inside Ledger Core.

ATOMIC-006:
Ledger Core SHOULD construct all required commit records before mutating authoritative state.

ATOMIC-007:
Failed commit MUST NOT expose partial state as committed.

ATOMIC-008:
Ledger Core MUST NOT await any inter-canister call after beginning authoritative state mutation and before commit completion.

ATOMIC-009:
Authoritative commit MUST be performed as one local Ledger Core state transition.

ATOMIC-010:
Read Model sync MUST occur only after Ledger Core commit and MUST NOT be required for commit success.

ATOMIC-011:
Gateway-to-Ledger-Core execution MAY cross canister boundaries before commit begins, but no cross-canister call may be inside the authoritative commit mutation sequence.

ATOMIC-012:
CommitPlan construction and invariant validation MUST complete before any authoritative mutation is applied.

ATOMIC-013:
Any implementation requiring a separate Journal Canister for MVP authoritative commit violates atomicity and ADR-001.

immediateCallerPrincipal != originalCallerPrincipal in Gateway-mediated Ledger Core execution.
